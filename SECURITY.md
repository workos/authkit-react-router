## Reporting a vulnerability

## Advisories

### v0.11: OAuth state CSRF / session fixation {#v011-csrf-fix}

**CWEs:** [CWE-352 — Cross-Site Request Forgery](https://cwe.mitre.org/data/definitions/352.html), [CWE-384 — Session Fixation](https://cwe.mitre.org/data/definitions/384.html)

**Affected versions:** `@workos-inc/authkit-react-router` < 0.11.0

**Fixed in:** 0.11.0

#### Summary

Prior to 0.11.0, the OAuth `state` parameter generated by `getAuthorizationUrl`
was an unsigned base64-encoded JSON blob containing only `returnPathname`. The
callback (`authLoader`) accepted any `state` value without verifying that it
originated from the same browser that initiated login. There was no per-flow
nonce, no server-held secret binding state to the initiating browser, and no
PKCE code verifier.

An attacker could mint any `state` value, initiate a login flow with their own
credentials, and trick a victim's browser into completing the callback —
logging the victim into the attacker's account (login-CSRF). The unbound state
also enabled pre-generated flows to fix a victim's session.

The same vulnerability existed on three re-authentication paths in
`src/session.ts` (refresh-failure, `ensureSignedIn` no-session,
`refreshSession` no-cookie): each redirected to the authorization URL without
any browser binding.

#### Fix

Three defensive layers are composed at every authorization request:

1. **Sealed, signed state** — the URL `state` parameter is now an
   `iron-session`-sealed blob containing a per-flow UUID nonce, the PKCE
   `codeVerifier`, and a sanitized `returnPathname`. Tampering fails signature
   verification.
2. **Double-submit cookie** — the same sealed value is stored in an
   `httpOnly` `__Host-wos-auth-verifier` cookie on the initiating browser.
   The callback requires a byte-equal match between URL `state` and cookie,
   binding the flow to one browser. `__Host-` prefix defeats cookie-tossing
   from sibling subdomains.
3. **PKCE (S256)** — even if an attacker obtains an authorization code, they
   cannot exchange it without the `codeVerifier` that only the initiating
   browser's cookie contains.

#### Breaking changes

`getSignInUrl` and `getSignUpUrl` have been replaced with throwing stubs that
emit a migration URL. The secure replacements are `redirectToSignIn(options?)`
and `redirectToSignUp(options?)`, which return a `Response` with both the
`Location` header and the `Set-Cookie` header baked in. See the
[CHANGELOG](./CHANGELOG.md) and [README](./README.md) for the full migration
guide.
